# Performance and limits

The measured development target is creation, membership, repository access and agent communication within 60 seconds on a reachable network. A disconnected network cannot meet that deadline. Downloading all assets is constrained by their byte size and the actual path throughput.

## Actual bottlenecks removed

- Initial event synchronization inherited a 45-second long-poll default. It now explicitly uses `wait=0`. Background delivery waits 10 seconds, with a 15-second request deadline.
- The actual Linux HTTP handler showed about 41 ms per persistent request with TCP_NODELAY off and 0.16–0.28 ms with it on in an isolated A/B test. Production persistent health now measures 0.256–0.351 ms after its first request.
- Pooled pinned SSH and HTTP avoid repeated handshakes. A restricted LAN route uses hostname discovery instead of a stale WiFi address.
- Certificate-verified HTTPS provides compatibility when a transparent VPN intercepts SSH. Windows invitation commands select HTTPS. Existing identities and SSH entrances are preserved.
- Git LFS batch action URLs are translated by an authenticated loopback proxy. Private server credentials never appear in Git remote URLs. A 1 MiB payload was uploaded and independently downloaded with exact byte comparison.
- Busy Desktop delivery uses its existing-turn steer operation. Idle delivery uses official Codex queue. Raw turn/start is disabled. Actual busy bidirectional messages 689/691 and read receipts were observed in the same existing Mac turn. Version 0.2.2 also passed delivery between two distinct existing Mac chats: message 729 started the idle recipient through Codex queue, and reply 739 entered the busy sender through Desktop steer. Both were actually read and acknowledged. Windows busy/idle behavior still requires live verification.

A fresh post-fix message 742 automatically woke the idle chat; reply 743 automatically entered the busy chat. Both agents recorded actual read receipts without a human forwarding or asking them to check messages. The server's own clock measured 24.878 seconds from the first message to its read receipt and 7.842 seconds from the reply to its read receipt, or 32.885 seconds for the complete communication exchange. This includes model scheduling and execution. The earlier message 729 waited almost 20 minutes for the idle-state bug to be fixed; it is not a successful latency measurement. Cross-host journal timestamps are not used for sub-second claims because their clocks differ and the journals have whole-second precision.

Killing only the new HTTPS outbound tunnel process produced temporary request failures, followed by an authenticated HTTPS manifest response after 6.821 seconds, measured with one client's monotonic clock. Systemd restarted the process. The legacy tunnel, review tunnel, local Atlas and local Gitea remained active. This tests tunnel-process recovery, not moving the entire laptop to a different WiFi.

## Physical and hardware bounds

[The BIPM defines vacuum light speed](https://www.bipm.org/en/measurement-units/si-defining-constants) as exactly 299,792,458 m/s. For required propagation distance d, RTT is at least 2d/c. For an optical path of actual length L and effective group index n, its propagation contribution is 2nL/c. [Corning's SMF-28 Ultra specification](https://www.corning.com/content/dam/corning/media/worldwide/coc/documents/Fiber/product-information-sheets/PI-1424-AEN.pdf) gives n=1.4682 at 1550 nm. This is a fiber example, not proof of which fiber an ISP uses. At 10,000 km, vacuum RTT is at least 66.713 ms; that fiber model yields 97.948 ms before switching and queuing. This distance is illustrative: actual device cities and cable route lengths have not been established. Proxy-node detours must be included, not replaced by the endpoints' geographic distance.

For B bytes on a path with usable bottleneck C bit/s, serialization time is at least 8B/C. End-to-end throughput cannot exceed the slowest access link, relay, encryption engine, storage or CPU service stage. Observed throughput does not identify every link's capacity.

The server is a Ryzen 7 5800H with 16 logical CPUs. Reported maximum clock is 4.465261 GHz, corresponding to a 0.224 ns clock period. Its observed clock varies with power management. A critical chain of q CPU cycles needs at least q/f_max; instructions are not equivalent to clock cycles. The measurements below count one observed worker's CPU execution, not every possible implementation's critical chain. Eliminating a measured 0.3 ms backend stage can save at most 0.3 ms for that request; it cannot eliminate a 600 ms network path. The WiFi reported 866.7 Mbit/s PHY rates over 80 MHz. That is not usable Internet capacity: airtime sharing, retransmission, protocols and upstream links reduce it.

An isolated test subsequently measured real per-thread hardware counters on the laptop, using the actual deployed Handler and Store with a fresh one-actor database. Each endpoint received 500 requests over one persistent connection. No production messages or credentials were used. Hardware counter running time equaled enabled time, so no multiplex scaling was needed. `/health` averaged 445,229 cycles and 361,016 instructions per request; `/v1/manifest` averaged 621,234 cycles and 512,810 instructions. Corresponding client-observed medians were 0.184 and 0.223 ms. At the reported maximum clock, the observed worker's CPU occupancy cannot be less than about 0.100 and 0.139 ms for that observed cycle count. These counts include the worker's kernel execution and exclude client CPU, SSH and TLS. They do not prove another implementation cannot reduce q. The small fixture also does not reproduce a large production grant table. Raw counters are in `evidence/cpu-cycles.json`.

## Pareto frontier and marginal cost

The currently measured choices trade compatibility, latency and added operation: LAN is about 8.64 ms and needs local reachability; HTTPS is about 601.43 ms and works through ordinary 443 paths using existing infrastructure. Both are retained. There is no extra VPS fee for this deployment. Native supervision, cursors and keepalives provide reconnection without model polling.

A per-socket physical-interface TCP probe reached the same relay SSH banner in 474–631 ms, compared with 736–779 ms via the existing TUN route. It was not an authenticated tunnel or throughput A/B, so no production routing change or claimed speedup follows from that probe. Changing relay location or path could improve WAN performance. Its price and operating cost have not been measured.

An authenticated tunnel A/B was then run against the same relay and the same Atlas/Gitea processes. A temporary restricted reverse tunnel used a socket bound to the physical WiFi interface; the existing tunnel continued through Mihomo. Socket inspection confirmed the physical interface and the existing TUN source separately. Both SSH tunnels were established concurrently. Request order alternated. Each route used 12 persistent health samples and three verified 1 MiB private LFS downloads; these are achieved rates, not access-line capacity tests. The temporary tunnel, two loopback-only port grants and temporary relay credentials were removed afterwards. All three production tunnel PIDs stayed unchanged.

| Relay-to-server route | Persistent health median | Fresh HTTP, one sample | LFS median Mbit/s | LFS observed range Mbit/s |
|---|---:|---:|---:|---:|
| Existing TUN | 242.593 ms | 481.740 ms | 3.568 | 3.567–6.092 |
| Physical WiFi socket | 229.759 ms | 451.339 ms | 3.192 | 3.081–3.351 |

The physical route saved about 12.834 ms (5.3%) on the persistent health median and did not improve these bulk samples. The production route was retained: forcing one interface adds privilege and an interface dependency, while Ethernet or another interface needs an additional selection/fallback mechanism. The small sample does not establish a universal winner. Even 15 sequential calls would save only about 0.193 seconds at that median difference, conditional on the same segment and no other bottleneck. These relay-local observations exclude the user's public TLS/Cloudflare/client-proxy legs and model scheduling. They cannot be substituted for whole-path latency. Raw samples are in `evidence/route-tun-vs-physical.json`.

A rational stopping calculation is H > N × delta / 3600, where H is added engineering/operation hours, N is expected operations over the decision horizon, and delta is seconds saved per operation. For example, saving 0.3 ms over 10,000 operations saves only 3 seconds; a backend rewrite is hard to justify for that narrow gain. This is a conditional decision rule, not proof that all further optimization is uneconomic. Large asset transfer and WAN routes have a different payoff.

A separate captain-Mac client A/B retained the same HTTPS hostname and normal certificate validation while comparing Cloudflare, the existing TLS origin directly, and an origin socket bound to the actual WiFi interface. No system route or VPN setting changed. Established connections coexisted, request order rotated, and the bound socket's interface option and local source address were verified. Ten persistent HTTP/1.1 health samples had medians of 753.073, 550.169 and 485.734 ms respectively. Three byte-verified private LFS samples per route had achieved median rates of 5.991, 5.106 and 7.293 Mbit/s, with substantial overlapping variation.

Because the CLI enables HTTP/2, a native Go probe then repeated the three health routes with certificate validation and confirmed **HTTP/2.0** on all three. Ten persistent samples per route had medians of 571.119, 553.072 and 497.522 ms. These are a separate run, not a controlled HTTP/1.1-versus-HTTP/2 speedup claim. They reject using the earlier HTTP/1.1 difference as the expected CLI gain. Direct origin saved only 18.047 ms (3.2%) relative to Cloudflare in the native Go sample. Fifteen sequential calls would conditionally save about 0.271 seconds. Keeping a fixed origin-IP hint and fallback adds lifecycle work for that narrow gain. Binding the Mac's WiFi socket saved 73.597 ms (12.9%), or about 1.104 seconds for those hypothetical fifteen calls, but adds interface selection and platform-specific behavior; Ethernet and independent Windows clients were not tested. Neither alternative was made the default. These samples do not establish performance for other teammates, future networks or every asset size. Raw results and standalone probes are in `evidence/client-routes-http1.json`, `evidence/client-routes-http2.json`, `evidence/client-route-probe.py` and `evidence/client-http2-probe.go`.

A free temporary Cloudflare Tunnel alternative was tested with a dedicated synthetic origin, exposing only health JSON and random bytes. No production upstream or credentials were connected. Its normal server route registered at `lax01`; eight native Go HTTP/2 health observations had a 639.811 ms median versus 583.639 ms for the existing public Atlas health. A second run gave only the probe's temporary DynamicUser a main-table routing exception and a private resolver mount. Socket inspection confirmed physical WiFi egress; it still registered at `lax01`. That stage had medians of 520.241 ms for synthetic health and 568.149 ms for the original service. Two 8 MiB synthetic downloads achieved 22.036 and 31.655 Mbit/s. Different handlers and separate runs limit causal attribution. This is not a domestic regional path or production acceptance. All temporary tunnel processes stopped, the single UID rule was removed, the old route-rule list was exactly restored and all three production tunnel PIDs remained unchanged. Quick Tunnels have unstable hostnames, no uptime guarantee and no SSE support, so this prototype was not adopted as the production entrance. See `evidence/temporary-cloudflare-route.json` and [the vendor's limits](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/).

**No global optimality claim is established.** The physical path, every capacity, alternative relay cost, independent Windows flow and relocation recovery need stronger evidence. The tested changes remove specific waste; they do not prove the network has reached its physical limit or that every further improvement costs too much.

Version 0.2.1 prefixes newly generated operation identifiers with a valid letter. Version 0.2.0 used base64url identifiers whose first character could be rejected by the server. Existing credentials stay valid, and invalid pending enrollment identifiers are repaired without changing the pending credential.

Version 0.2.2 falls back to the idle queue when Desktop explicitly rejects steering because the active turn already ended. Unknown delivery failures remain uncertain and are not blindly retried. Sending from an agent uses its current chat identity rather than another chat's last saved binding.
